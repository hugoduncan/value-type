# JEP 401 EA capabilities and JVM flags

## Scope

This reference covers Valhalla **`27-jep401ea3+1-1`**, the build selected by
[the JVM facts](../dev/jvm/jvms.edn). It summarizes capabilities used by
value-type, not every feature in the EA distribution. JEP 401 value classes,
strict field initialization and internal Valhalla APIs are separate parts of
this runtime. Do not treat every facility below as a public JEP 401 API.

Use the [runtime guide](../doc/development/runtime.md) for installation and
test commands. Recheck behavior and flags before changing the EA build.

## Capabilities

| Facility | Meaning | Library contract or boundary |
|---|---|---|
| Value classes | Objects have no identity; instance fields are final. | `defvaluetype` and `defvaluetype*` select value or identity representation. |
| Strict field initialization | The constructor initializes strict fields before the superclass constructor call. | The bytecode transform follows the EA class-file rules. This is not a null restriction. |
| Native null-restricted fields | Eligible value-class fields reject null through JVM enforcement. | `:non-nil` uses native restriction when eligible and available; otherwise it uses generated constructor checks. |
| Field flattening | The JVM can store a value payload within its containing object. | A non-nil field does not guarantee flat storage. |
| Null-restricted atomic arrays | Array slots reject null and have atomic element access. | `make-array` and `into-array` require native allocation; there is no ordinary-array fallback. |
| Array flattening | The JVM can store element payloads within the array. | Allocation eligibility does not guarantee flat storage. |
| Array diagnostics | The internal API reports null restriction, atomic access and flat storage separately. | `array-info` reports these properties for reference arrays. |

Value equality is not Clojure collection equality. In value mode, `identical?`
compares value state; identity-valued fields compare by reference. Identity
operations such as locking are not available. See
[semantic differences](../doc/usage.md#differences-from-deftype).

Native fields use `jdk.internal.vm.annotation.NullRestricted` with eligible
storage. Generated checks preserve the public non-nil constraint, including
on identity fallback, but do not create native null-restricted storage.
See [non-nil field design](non-nil-field-design.md).

## Required JVM flags

These are flags for the Java executable. With the Clojure CLI, prefix each
with `-J`.

| Operation | Required flags on the selected EA build |
|---|---|
| Define and use value classes | `--enable-preview` |
| Construct native non-nil fields through this library | `--enable-preview`; no internal-package export |
| Allocate native null-restricted value arrays | `--enable-preview` and `--add-exports=java.base/jdk.internal.value=ALL-UNNAMED` |
| Inspect ordinary reference arrays through the internal diagnostics | `--add-exports=java.base/jdk.internal.value=ALL-UNNAMED`; preview is not required |
| Use identity fallback with generated non-nil checks | Neither flag |

The field row concerns generated bytecode, not Java source that imports the
internal annotation. Source compilation can have separate module-access
requirements. The export shown here targets classpath code in unnamed modules.

Start a Clojure process with value classes and array access:

```sh
export JAVA_CMD=<valhalla-jdk-home>/bin/java
clojure -J--enable-preview \
  -J--add-exports=java.base/jdk.internal.value=ALL-UNNAMED -M
```

API discovery is not proof of access. With preview but no export, value
creation can succeed while array allocation access fails. With the export but
no preview, diagnostics on ordinary arrays can succeed without establishing
value-array allocation capability.

## Optional layout and test controls

| Flag | Purpose |
|---|---|
| `-XX:+UseFieldFlattening` / `-XX:-UseFieldFlattening` | Enable or disable field flattening. |
| `-XX:+UseArrayFlattening` / `-XX:-UseArrayFlattening` | Enable or disable array flattening. |
| `-Xint` | Run interpreter-only semantic controls; not a feature requirement. |

Enabling flattening permits a layout choice; it does not force every field or
array to be flat. These controls are not additional null-restriction flags.
The runtime guide tests both settings. Do not infer defaults for other builds.

`-XX:+UnlockExperimentalVMOptions` appears in the
[benchmark configuration](defvaluetype-design/benchmark.md#environment) with
the Criterium blackhole compile command. It is not part of the required
value-class or array launch profiles.

## Semantics, layout and evidence limits

Keep null restriction, atomic access and flattening separate:

- Ordinary Object arrays can report atomic access without null restriction.
- A value object can contain a nullable field while remaining a valid non-null
  array element.
- In the recorded array fixtures, a restricted one-long array is flat; a
  restricted two-long array is not. Both are eligible and atomic.
- Disabling array flattening preserves null rejection, contents and atomic
  diagnostics in those fixtures.
- Atomic element access does not make compound updates atomic or establish
  safe publication. Sequential tests do not prove concurrent behavior.
- Flat storage alone proves neither a size reduction nor a speed improvement.

The [array semantic report](value-type-array-design/semantic-verification.md)
records fixtures, startup combinations and retained evidence on EA3,
Clojure 1.12.6 and macOS ARM64. Those observations are not universal layout
rules. It also records native diagnostic crashes on null input: use the
validated public API, not unchecked internal calls.
